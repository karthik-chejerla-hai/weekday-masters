# Data model and migration design

Design baseline: PR #103 merged at `9b83151`; no schema changes are implemented here.
All IDs are UUIDs generated by model hooks, with client-proposed IDs validated where
needed to keep previews deterministic. Amounts are signed BIGINT integer cents.
There is one club in the existing schema; do not introduce multitenancy in this work.

## MoneyOperation — new table `money_operations`

Fields: `id` UUID PK (submission/request identity); `actor_id` UUID NOT NULL FK
users; `action` text enum `correct_topup|reverse_transaction|create_shared_expense|
correct_shared_expense|correct_settlement`; `target_transaction_id` nullable UUID
FK transactions DEFERRABLE INITIALLY DEFERRED; `payload_hash` CHAR(64) NOT NULL;
`canonical_payload` JSONB NOT NULL; `response_status` smallint; `response_body` JSONB; `created_at` timestamptz
NOT NULL; `sequence` BIGINT generated by a database sequence, unique, NOT NULL.
Sequence is only an ordering tie-breaker, not an accounting number or public ID.

Unique request ID is global within this club. A different actor cannot retrieve
another actor's replay. The target FK is deferred so reservation does not take a
premature KEY SHARE lock that competing requests later upgrade to FOR UPDATE on the original.
The full canonical request includes action, target, reason,
proposed IDs, normalized inputs and accepted fingerprint. A failed transaction
rolls back its reservation. No committed pending row is allowed: status/body must
be populated before commit. The row becomes immutable on successful commit and
has no TTL; historical retry safety must survive restarts and deployments.

Store a bounded response DTO with original/reversal/replacement IDs, accepted
review and links, not tokens, email addresses or an ORM object graph. Response
balances are those confirmed at that time; the UI refetches live balances on replay.
There are no foreign keys inside stored JSON; typed transaction links carry those
relationships. Keep old schema readers compatible by adding fields/tables first.

## Transaction — extend existing `transactions`

Reuse `reverses_transaction_id` (unique), `corrects_transaction_id` (unique),
`correction_reason`, description, actor and effective/recording timestamps.
Add nullable `money_operation_id` UUID FK MoneyOperation and nullable
`operation_step` smallint. Both must be null for old transactions or non-null
together. For a standalone create or reversal step is 0. For correction the
inverse has step 0 and replacement step 1; unique `(money_operation_id,
operation_step)` prevents duplicates. No new mutable status column is necessary.
Add kind `shared_expense` to the application's enum; PostgreSQL stores a string.

State is derived: a transaction with a linked inverse is `corrected` when a
replacement exists, otherwise `reversed`; an original/replacement without an
inverse is `active`. Reversal rows are never actionable. A replacement uses the
same native kind as the transaction it replaces. Its correction link points to
its immediate predecessor, not the root. Exact-original uniqueness serializes
competing correction and reversal, including legacy routes.

Only reversal metadata on the associated settlement is mutable. Never rewrite
old transactions, dates, ledger values, recorded allocations or charge lines.
A reason is stored on the inverse and replacement via existing reason fields;
standalone reversal receives the reason too, rather than relying only on its title.

## SharedExpenseVersion — new table `shared_expense_versions`

Fields: `id` UUID PK; `expense_id` UUID NOT NULL (stable root identity and split
seed); `transaction_id` UUID NOT NULL UNIQUE FK transactions; `category` enum
`food|other`; `description` trimmed text 1–1,000 Unicode characters;
`bill_cents` BIGINT > 0; `funding` enum `personal|club_bank`; `split_mode` enum
`equal|custom`; `session_id` nullable UUID FK sessions with RESTRICT deletion;
`expense_date` DATE NOT NULL (Sydney date); `created_at` timestamptz NOT NULL.
The transaction stores the resolved effective instant, authoritative for ordering.

For creation the proposed expense ID equals proposed first version ID; corrections
supply a new version ID and inherit the original expense ID. Validate root identity
against the target; clients cannot choose a different seed during correction.
Version ID and root identity are not the submission ID. A request UUID can be
retained through refreshed review without changing deterministic allocations.
Index `(expense_id, created_at, id)` and `(session_id)`; transaction links identify
immediate predecessor/current version, avoiding a mutable root pointer.

Every version and allocation is immutable. A reversal adds a transaction but no
replacement version. Readers attach the original gross allocation to its inverse
and label its financial effect as the exact negation, not a fresh expense.

## SharedExpenseAllocation — new table `shared_expense_allocations`

Fields: `id` UUID PK; `version_id` UUID NOT NULL FK versions RESTRICT;
`user_id` UUID NOT NULL FK users RESTRICT; `paid_cents` BIGINT >= 0;
`owed_cents` BIGINT >= 0; `participates` BOOLEAN NOT NULL;
`created_at` timestamptz NOT NULL.
Unique `(version_id,user_id)`; index `(user_id,version_id)` for personal discovery.
Do not store a separate mutable balance or duplicate derived net.

Each row requires participates OR paid_cents > 0; a nonparticipant owes zero.
Each distinct payer or participant has exactly one row, including payer-only,
zero-net and explicit zero-share participants. At least one owed participant;
positive bill. Personal funding: sum paid = sum owed = bill. Club funding:
all member paid = 0, sum owed = bill. Membership validation uses the union of old
and new rows, so removing a row cannot hide a member's inverse effect.

Ledger legs per version: one per allocation, `paid - owed` for personal funding;
`-owed` for club funding plus bank `-bill`. Preserve zero-valued member legs.
No court, stock or surplus leg for either funding mode. Cross-row totals and
transaction identity are service checks under locks, with DB checks for individual
bounds and uniqueness. Add FKs/check constraints through the explicit migrator.

## Settlement and ChargeLine — extend snapshots

Reuse Settlement, ChargeLine, one-live-per-session index, saved rates, consumed
shuttle units/value and nullable `actual_shuttles` mode discriminator. Replacement
settlements link through their transaction's `corrects_transaction_id`.
Add nullable `base_court_cents` and `extra_court_cents` BIGINT snapshot columns;
new ordinary/replacement settlements populate exact nonnegative totals. Null means
legacy reconstruction is required, never zero or current defaults. Do not backfill
money by guessing. Reconstructed per-band decimal-hour totals must sum to the exact
original court debit, otherwise return `legacy_correction_unsupported`.

Add nullable ChargeLine `allocation_key` UUID. New lines receive a stable key;
for retained pre-upgrade lines use their existing line ID as the fallback identity.
Replacement rows receive new PKs but retain their allocation key. New guest lines
have distinct keys even for the same host; one member line per user, distinct guest
lines with nonblank guest name, no duplicate keys. Settleable bands must have a head
when their total is positive. Session correction preserves its original mode:
actual count is 2/3 hours, member-only, no comped/guest lines; legacy retains those
capabilities. Legacy hour/rate inputs use exact hundredths for new arithmetic.

For unchanged costs/attendance (metadata-only revision), copy original charges
exactly. For recalculation use stable keys with the session seed. Array reordering
alone is not a change. Keep original host/guest aggregation and comped surplus.

## Effective dates and order

New top-up/shared inverses use the original transaction's exact `occurred_at`.
Replacement defaults to that instant. A changed `occurred_date` resolves to Sydney
start of day; submitting the same date preserves the old instant. New shared
expenses resolve their chosen date to Sydney start of day. Reject future dates
by Sydney calendar date. Never compute days by adding 24h through DST.

Session replacements retain the original charge's effective instant, and expose
session play date separately; no date editor may move a charge to a different
session. Retain existing Sydney session-date spend semantics, including overnight
sessions. Recording time remains the actual operation timestamp, separately shown.

Use the common order defined in `contracts/history.md`. Do not update legacy
entry times or backfill old correction dates. Backdated corrections recompute
effective balances, not historical snapshots of what the screen once showed.

## Migration and rollout

1. In `backend/internal/database/db.go`, register MoneyOperation before new linked
   transaction fields are used, and the two shared models when their PR lands.
   Handle the operation→existing-transaction and transaction→operation FK cycle by
   creating tables/columns before adding FKs; reservation inserts reference an
   existing target only, and transaction rows reference an existing reservation.
2. Add nullable transaction/settlement/line columns first; no old entry edits.
   Add operation sequence/default, unique indexes and enum/check/FK constraints
   via `applyLedgerConstraints` or a dedicated idempotent migration helper.
3. Add each new table to `backend/internal/testsupport/db.go:truncateAll` in the
   same PR; test fresh creation and upgrade from populated pre-feature schema.
4. Ensure `SessionService.DeleteSession` and DB constraints refuse deletion of a
   session referenced by a shared version, like the existing game restriction.
5. Deploy additive schema with `cmd/migrate`, then backend, then frontend. All old
   fields/read envelopes remain available. Changing supported legacy reversal
   request requirements is coordinated with its client callers and API docs.
6. Old code cannot safely serve writes for a new shared kind. Before enabling the
   shared-expense UI, drain old backend revisions and ensure generic reversal
   type dispatch recognizes it. Rollback after new-kind records requires a backend
   version that recognizes that kind; disable new controls if retreat is needed.
   Do not drop financial tables or reverse migrations containing recorded data.

These are design steps for later PRs. No migration or production financial
operation is performed by this documentation change.
